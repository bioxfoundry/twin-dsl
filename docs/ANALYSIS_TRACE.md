# Analysis trace and version history

Each changed living-project iteration now emits a reviewable explanation of what the runtime
used, which explicit rules it applied, what it selected or refused, and which evidence gaps
remain. The report is an audit trail, not a model's private chain of thought: conclusions are
represented as source locators, bounded excerpts, deterministic rule IDs, confidence,
alternatives and outcomes.

## Files and storage

The runtime writes the candidate report before publication:

```text
.living-runtime/candidate/
  analysis-trace.json       machine contract: subactor.analysis-trace/v1
  analysis-trace.dsl        line-oriented AnalysisTraceDSL
  analysis-trace.md         human-readable report with links, quotations and DSL blocks
  analysis-manifest.json    SHA-256 manifest for the report and embedded DSL snapshots
```

If all publication gates pass, the same bytes are copied to `.living-runtime/current/`.
Rejected candidates never replace the active report.

Every changed evaluation also receives an immutable history directory, whether accepted or
rejected:

```text
.living-runtime/analysis-history/
  latest.json
  2026-08-12T10-00-00-000Z-<trace-hash>/
    analysis-trace.json
    analysis-trace.dsl
    analysis-trace.md
    analysis-manifest.json
    math.dsl
    process.dsl
    process-animation.dsl
    geometry-validation.dsl
    project-integrity.dsl
```

This data belongs with the project runtime because it must match the exact candidate/active
artifacts. Generator source, schema and tests stay in `twin-dsl`. A separate repository may
mirror selected, non-confidential history later, but must not become the authoritative write
path: asynchronous publication would allow the explanation and Twin revision to drift.

The machine contracts are published as `schemas/analysis-trace.schema.json`,
`schemas/analysis-trace-manifest.schema.json` and `schemas/analysis-trace-pointer.schema.json`.

## Version and comparison identity

Every report records:

- timestamp in UTC;
- package version and `RUNTIME_GENERATION` semantics identifier;
- source Git revision when available (`DT_RUNTIME_SOURCE_REVISION` may pin it in a container);
- project config, research snapshot, development, observation and intentDSL semantic hashes;
- content-addressed Twin, Scene, Process and ProcessAnimation URIs;
- hashes of the DSL snapshots stored with the report;
- structural changes in decisions and metrics relative to the previous active report.

Changing generation semantics requires bumping `RUNTIME_GENERATION`. That invalidates the
living-project stable key, causes unchanged sources to be re-evaluated, and makes the new method
visible in the next trace.

## Citation rules

Internal citations are produced from intentDSL `SourceAnchor`: artifact URI, source revision,
page/lines/fragment, converter/version and a bounded excerpt. From the dashboard, every internal
link passes through `/api/source`: the handler accepts only `subactor://markdown/...`, resolves it
under declared project/workspace source roots and returns bytes only when their SHA-256 equals the
recorded revision. It never accepts a filesystem path from HTTP. A source mirror therefore has to
be mounted beside a deployed project; otherwise the report stays auditable but the link fails with
`SOURCE_REVISION_NOT_FOUND` instead of showing drifted text.

External links are acquisition or publication locators and never prove that a particular physical
asset is installed. External assets require separate license, hash, units and component binding
before Physical Evidence Intake can ground them in the scene. The current Raspberry Pi candidates
use manufacturer documentation, while BIO-SPEC publication/source locators use DOI redirects.

Quoted excerpts are intentionally bounded. The complete local source remains linked and keeps
the converter/version provenance generated by f2md.

## Retention and repository boundary

`analysis-history/` is append-only and currently has no automatic deletion policy. Keep it out of
the source repository together with the other `.living-runtime/` state; each project owner can
back it up to content-addressed/object storage under its own confidentiality and retention rules.
If cross-project trend analysis is needed, export manifests and non-confidential reports to an
optional mirror repository. Do not move the generator or authoritative runtime write path there:
the report must be published by the same gated iteration as the candidate/current Twin revision.
